# Model Card: Fraud Detection Model v2

## 1. Назначение модели

Модель предназначена для **дополнения существующей правило-ориентированной антифрод-системы** в цифровом банкинге с целью:

- Повышения точности обнаружения мошенничества за счёт выявления сложных нелинейных паттернов в данных.
- Снижения доли ложных срабатываний (False Positive) за счёт вероятностной оценки риска вместо бинарных правил.
- Обеспечения адаптивности к изменяющимся тактикам мошенников через регулярное переобучение.

**Основные сценарии использования:**
- Real-time скоринг каждой входящей транзакции.
- Режим «shadow mode» (первые 2 недели — логирование прогнозов без влияния на решения).
- Мониторинг дрейфа данных и деградации качества через MLflow.

**Вне области применения:**
- Модель не предназначена для автоматического принятия решений без комбинирования с бизнес-правилами (Rule Engine).
- Не применяется к кредитному скорингу, KYC/AML-проверкам, небанковским операциям.

## 3. Входные данные

### 3.1. Признаки (18 фичей)

**Количественные (13):**

| Признак | Описание |
|---|---|
| `transaction_amount` | Сумма финансовой операции в валюте счёта |
| `anomaly_score` | Оценка аномальности от правило-ориентированной антифрод-системы |
| `account_age_days` | Возраст аккаунта в днях с момента регистрации |
| `login_attempts` | Количество попыток авторизации перед успешным входом |
| `transfer_frequency` | Частота исходящих переводов за фиксированный период |
| `failed_transactions_last_30d` | Число отклонённых транзакций за последние 30 дней |
| `avg_monthly_balance` | Усреднённый месячный остаток на счёте |
| `daily_transaction_count` | Среднее количество операций в сутки |
| `geo_distance_km` | Расстояние между геолокациями текущей и предыдущей транзакций |
| `session_duration_minutes` | Продолжительность пользовательской сессии в минутах |
| `transaction_velocity_score` | Метрика интенсивности проведения транзакций за короткий промежуток |
| `device_risk_score` | Оценка риска устройства на основе истории (0–100) |
| `transaction_time_hour` | Час суток совершения операции (0–23) |

**Категориальные (2):**

| Признак | Допустимые значения |
|---|---|
| `payment_channel` | POS-терминал, веб-банк, мобильное приложение, банкомат |
| `authentication_type` | OTP, биометрия, двухфакторная аутентификация, пароль |

**Бинарные флаги (3):**

| Признак | Описание |
|---|---|
| `card_present_flag` | Использование физической карты при транзакции |
| `international_transaction_flag` | Трансграничный характер операции |
| `suspicious_ip_flag` | Вход с подозрительного или анонимного IP-адреса |

### 3.2. Производные признаки (feature engineering)
- `transaction_amount_log` — логарифм суммы транзакции
- `geo_distance_km_log` — логарифм гео-расстояния

### 3.3. Требования к входным данным (валидация ETL)
- Отсутствие дубликатов строк
- `fraud_flag ∈ {0, 1}`
- Положительная сумма транзакции
- `device_risk_score ∈ [0, 100]`
- `login_attempts ≥ 0`
- `transaction_time_hour ∈ [0, 23]`
- Допустимые значения категориальных колонок
- Корректность логарифмических признаков
- Отсутствие бесконечных значений (`inf`)

## 4. Выходные данные

| Поле | Тип | Описание |
|---|---|---|
| `prediction` | int (0/1) | Бинарный прогноз (0 — легитимная, 1 — мошенническая) |
| `probability` | float (0..1) | Вероятность того, что транзакция мошенническая |

**Порог принятия решения (`threshold`)** настраивается; по умолчанию используется значение, оптимизированное под максимизацию Recall при контроле Precision.

**API-эндпоинты:**

| Метод | Путь | Описание | Ответ |
|---|---|---|---|
| GET | `/health` | Проверка работоспособности | `{"status": "ok"}` |
| POST | `/predict` | Предсказание по транзакции | `{prediction, probability}` |

**Коды ошибок валидации:**
- Пустые данные (`data: {}`) → 422
- Отсутствует поле `data` → 422
- Некорректный `threshold` (>1) → 422

## 6. Ограничения и особенности применения

### 6.1. Технические ограничения

| Ограничение | Описание |
|---|---|
| **Интерпретируемость** | Требуется SHAP/LIME для аудита и регуляторных требований (запланировано) |
| **Масштабируемость** | До 10 000 транзакций/мин |
| **Зависимость от правил** | Модель дополняет, а не заменяет Rule Engine |
| **Fallback** | При таймауте инференса (>500 мс) или ошибке загрузки модели — переход на правило-ориентированную систему |
| **Среда выполнения** | Python 3.10/3.11, Docker (`python:3.10-slim`), FastAPI + Uvicorn |
| **Регуляторное соответствие** | Все изменения документируются и проходят внутренний аудит |

### 6.2. Бизнес-ограничения и риски

| Риск | Митигация |
|---|---|
| Ложные блокировки легитимных клиентов | Precision (normal) ≈ 0.988, ручная проверка |
| Пропуск новых схем мошенничества | Регулярное переобучение, мониторинг дрейфа |
| Недовольство клиентов | Shadow mode (2 недели), снижение FP на 30% |
| Регуляторные нарушения | Документирование, внутренний аудит, SHAP/LIME |

### 6.3. Особенности применения

- **Консервативный запуск:** первые 2 недели — режим «shadow mode» (прогнозы логируются, но не влияют на решения).
- **Регламент переобучения:** при появлении нового `.pkl` в `models/` → автоматический запуск `deploy_model.yaml`; рекомендуемая периодичность — не реже 1 раза в месяц или при обнаружении дрейфа.
- **CI/CD:** GitHub Actions (2 workflow: `data_processing.yaml`, `deploy_model.yaml`), Docker-образ публикуется в GitHub Container Registry (`ghcr.io`) с тегами `:latest` и `:{git_commit_sha}`.
- **Тестирование:** 10 тестов валидации данных (pytest) + 4 теста API (модульные и интеграционные).

### 6.4. Этические аспекты
- Модель **не использует** защищённые атрибуты (пол, возраст, раса, религия) напрямую.
- Косвенные прокси-признаки (`geo_distance_km`, `device_risk_score`) требуют регулярного аудита на предмет дискриминации.
- Все решения, влияющие на клиента, должны быть объяснимы (SHAP/LIME).

### 6.5. Вне области применения
- Модель не предназначена для автоматического принятия решений без комбинирования с бизнес-правилами.
- Не применяется к кредитному скорингу, KYC/AML-проверкам, небанковским операциям.
